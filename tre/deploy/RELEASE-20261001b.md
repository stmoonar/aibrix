**Short double write during the plugin rollout.** `tre-gateway-plugins` has 1 replica,
RollingUpdate (maxSurge 25 % -> 1): the old and the new plugin pod run side by side until
the new one is Ready and the old one has terminated (tens of seconds). Both write every
model pod's instant / histogram docs for the same 10 s boundaries. The new pod replaces
its own doc of a boundary (ZREMRANGEBYSCORE + ZADD), but an old pod's doc of the same
boundary is a different member (no `written_ms`), so those boundaries hold two docs and
the controller, which sums a window's instant docs, sees up to twice the TSS numerator for
the windows that cover the overlap. That is why the swap runs in `observe observe`, and:

- after `rollout status`: `redis-cli ZRANGE tre:v2:gw:instances 0 -1 WITHSCORES` lists only
  the new pod, score advancing;
- wait **>= 40 s** (one 30 s window + one grid) after the old pod is gone before relying
  on Z_m (i.e. before section 7's `observe active`); a later boundary then holds exactly
  one doc: `redis-cli ZCOUNT tre:v2:inst:<ns>/<pod> <B> <B>` = 1 for a recent boundary
  `B`, and the newest doc carries `written_ms`;
- until all docs carry `written_ms` the controller's clock check uses the stamp-lag
  fallback (no verdict change expected).

Checkpoints after each component: pod Running, no restart; images = `$TAG`.
- SM: registry OK, supervisor running, `GET /v2/wake` answers (no code change since
  bba6fc55).
- controller: starts, no traceback; the controller does not log its `scaling` config,
  read it from the pod after section 4:
  `kubectl -n tre-v2 exec deploy/tre-v2-controller -- python3 -c "from tre_common.registry import load_registry; print(load_registry('/etc/tre/registry.yaml').scaling())"`
  (breakpoint_window True, rescue_max_step_pods 4, scale_up_cooldown_enabled False); no `breakpoint_window_suspended`

2. tre-v2: `DROP_KEYS=tre:v2:controller:scale_memory DROP_SCAN= SKIP_MODELS=1 SKIP_ENVOY=1
   bash $B/rollback.sh` - registry ConfigMap back, then controller -> SM -> plugin -> UI

   writes it; left behind, a later re-upgrade would restore a rescue target of a past
   episode (the 50 s age cut-off drops old ones, but a quick re-upgrade could still pick
   one up). The plugin rollback has the same short double write (old docs without
   `written_ms` next to new ones): stay in observe >= 40 s afterwards.

## Risks

- **Double counting during the plugin swap** (section 3): bounded to the overlap plus one
  window; covered by observe + the 40 s wait.
- **Clock check**: O1 compares controller time with gateway stamps; a node clock drift
  > 2 s suspends O1 (falls back to the onset guard) - visible as
  `breakpoint_window_suspended`; 75 has drifted ~160 s before.
- **Aggressive rescue**: `rescue_max_step_pods` 4 lets n = 1 jump to 4 in one decision;
  combined with O1's earlier decisions this is the intended change, but it can wake
  donors' GPUs faster than before - watch C and A-TRE for refused wakes / cooldowns.
- **APA arm semantics** change with the CRs (window 20 s instead of 180 s, tolerances up
  0.1 / down 0.2 = v1's effective values instead of v2's 0.1 / 0.1, no scale-down cooldown
  instead of 300 s); APA numbers before and after this release are not the same baseline.
- **controller-manager** is shared AIBrix infrastructure; its image is the only
  aibrix-system change; rollback is a single `set image` to the immutable tag.

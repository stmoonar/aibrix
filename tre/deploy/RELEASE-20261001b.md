**Short double write during the plugin rollout (UP only).** `tre-gateway-plugins` has 1
replica, RollingUpdate (maxSurge 25 % -> 1): the old and the new plugin pod run side by
side until the new one is Ready and the old one has terminated. Both write every model
pod's instant / histogram docs for the same 10 s boundaries. The new pod writes a
boundary as ZREMRANGEBYSCORE + ZADD in one transaction, which removes **every** doc of that
boundary - the old pod's included; a boundary holds two docs only when the old pod writes
it **after** the new pod (an old pod's doc has no `written_ms`, so it is a different
member and ZADD keeps both). The controller sums a window's instant docs, so such
boundaries inflate the TSS numerator of the windows covering them, and the EMA carries
part of it into later ticks. Hence:

- the swap runs in `observe observe`;
- after `rollout status`: `redis-cli ZRANGE tre:v2:gw:instances 0 -1 WITHSCORES` lists only
  the new pod, score advancing;
- wait **>= 90 s** after the old pod is gone before relying on Z_m (section 7's
  `observe active`): one 30 s window plus several EMA time constants
  (`trs.ema_tau_ms`); 40 s still leaves a visible part of an inflated window in the EMA.
  Or compare: `$R GET tre:v2:decision:latest` per model back to the level of
  `/tmp/decision-before-$TAG.json` (same load) before switching;
- a recent boundary `B` then holds exactly one doc (`redis-cli ZCOUNT tre:v2:inst:<ns>/<pod>
  <B> <B>` = 1) whose member carries `written_ms`;
- until all docs carry `written_ms` the controller's clock check uses the stamp-lag
  fallback (no verdict change expected).

`Recreate` for the plugin is not an option: the Envoy extension runs with
`failOpen: false`, so a moment without any plugin pod answers 5xx to every request. With
the models DOWN there are no docs and nothing to wait for.

## Rollback (any failure)

`B=$(cat $BPATH)` first.

1. `set_run_mode.sh observe observe`.
2. tre-v2: `DROP_KEYS=tre:v2:controller:scale_memory DROP_SCAN= SKIP_MODELS=1 SKIP_ENVOY=1
   bash $B/rollback.sh` - registry ConfigMap back, then controller -> SM -> plugin -> UI
   as whole Deployment objects (7994da76's images), then `tre:v2:controller:scale_memory`
   deleted once the old SM runs. Why delete it: the old controller neither reads nor
   writes it; left behind, a later re-upgrade would restore a rescue target of a past
   episode (the 50 s age cut-off drops old ones, but a quick re-upgrade could still pick
   one up). UP: the plugin rollback has the same short double write: stay in observe
   >= 90 s afterwards.
3. AIBrix (only if section 5 ran): `$B/rollback-controller-manager.sh` - it checks the
   pod's imageID starts with `docker://sha256:4c658acb5caf` and shows the lease. APA CR
   files: re-apply the old ones from the running branch if the window / tolerance keys
   must go back (they are only applied on the APA arm).
4. `tre_models.sh` (only if 7.4 ran): `cp -p "$(cat $B/tre_models-backup.path)" $TRE_MODELS`;
   `grep -n '^WT=' $TRE_MODELS` shows the old default again.
5. Redis state only if corrupted: `RESTORE_REDIS=1` (controller + SM scaled to 0 meanwhile).
6. `GET /v2/audit` once; run mode from `$B/run-mode.txt` (DOWN: stays `observe observe`);
   `rm -f $WIN`.

## Risks

- **Double counting during the plugin swap** (UP, section 4): only when the old plugin
  pod writes a boundary after the new one; bounded to the overlap plus the window / EMA
  tail; covered by observe + the 90 s wait (or the Z_m comparison).
- **GPU take-back** (DOWN): any `observe active` / `active active` while model
  Deployments are missing lets fleet repair re-create them on the lent GPUs - hence the
  hard gate in section 7 and `tre_models.sh up` as the only way back.
- **Clock check**: O1 compares controller time with gateway stamps; a node clock drift
  > 2 s suspends O1 (falls back to the onset guard) - visible as
  `breakpoint_window_suspended`; 75 has drifted ~160 s before.
- **Aggressive rescue**: `rescue_max_step_pods` 4 lets n = 1 jump to 4 in one decision;
  combined with O1's earlier decisions this is the intended change, but it can wake
  donors' GPUs faster than before - watch C and A-TRE for refused wakes / cooldowns.
- **APA arm semantics** change with the CRs (window 20 s instead of 180 s, tolerances up
  0.1 / down 0.2 = v1's effective values instead of v2's 0.1 / 0.1, no scale-down cooldown
  instead of 300 s); APA numbers before and after this release are not the same baseline.
- **controller-manager** is shared AIBrix infrastructure; its image is the only
  aibrix-system change, behind an explicit confirmation; its window behaviour is only
  observable once APA CRs exist (section 8 B); rollback is a single `set image` to the
  immutable tag.

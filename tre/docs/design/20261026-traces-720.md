# 720 s trace 集（2026-10-26，分支 `feat/traces-720-20261026`）

用户 10-26 定：campaign 的 trace 全部改成 720 s（和 v1 一样），Prefill 输入不超过 8192；按 Alternating → T7 的教训重设计合成 trace，使每条 trace 的性质和名字一致；Real_code / Real_conv 不改。设计经独立评审（Fable 5.1）后由主会话定稿。本文是**预注册**：所有预期都在任何一臂运行之前写下。

- 生成器：`tre_replayer.tracegen`（本分支）；脚本 `replayer/scripts/generate_traces_v2.sh`。
- 数据：`<data root>/traces-v2-720-20261026/`（旧集 `traces-v2-vslo-20261007/` 不动）。数据不进 git。
- 容量：`tracegen/data/capacity_20261007_vslo.json`（ρ = 1 = 一个副本在 V_slo，V_slo = 0.9·V_b），没有改。

## 1. 方法：保留段长，减少重复
v1 的 trace 是 720 s、短事件（40–72 s）多次重复；v2 的事件按 R2 ≥ 150 s。缩到 720 s 时保留每个事件的时长和形状，减少重复次数（整体压缩时间轴会把段压到 100–160 s，违反 R2，而且改变了要测的东西：决策延迟约 20–30 s 占段长的比例）。每条 trace 第一个事件在 ≥ 60–90 s（30 s trim + 启动沉降）。

## 2. 新增审计规则
- **R7 争用**（1 s 设计网格）：Σ_m ceil(ρ_m)·gpus_m（按 V_slo 需要的卡）和 Σ_m ceil(0.9·ρ_m)·gpus_m（TokenScale 的 knee 视角）超过 8 的秒数；各模型设计 ρ 落在 TokenScale knee 盲带 (k, k/0.9]（k = 1..3）的秒数（平台段和全部）。`audit.r7.contention: true` 要求两种需要都超过 8；`false` 要求在过载窗以外、在加法单位和按形状的单位下都不超过 8（允许不超过一个 3 s 爬坡的过渡）。`blind_band_free` 要求平台段不在盲带内。
- **R8 预注册决策点**（流体队列）：每个模型的工作按设计 ρ 到达，按 n/0.9（knee）服务；超过就积压发散，低于就排空。选项 = 从 start + lag 到 end + lag 的副本分配（其余时间为基线 2/2/2）。到达的请求在积压等待 > 0.5 s 时算违约，否则按每副本负载 u：违约概率 (u − 1)/(1/0.9 − 1)，截在 [0, 1]（V_slo 处为 0，knee 处为 1）。在 [start, until) 上算违约请求数（V_req）和最差模型的违约比例（max-min）；预期选项在两种口径下都排第一才算满足（lag 30 s 判定，60 s 同时报告）。
- **按形状的容量**（`tracegen/shape.py`，`data/shape_capacity_20261019.json`）：每 30 s 的请求均值 (in, out, out²) 上，knee = min(计算 knee（加法模型）, KV knee)，KV knee = C·(in+out)/(ttft + out·tpot_kv)，C = min(256, KV/ctx)，ctx = in + E[out²]/(2E[out])（Little 定律；公式和数值来自 e1-envoy4 shape-analysis，8b 预测 2.67 对实测 2.74）。按形状的 ρ = 设计 ρ × 该 30 s 的形状因子（不受泊松噪声影响），用于 R7 = false 的判定；同时报告实现的 30 s 值。
- **输入上限**：没有 prompt 超过 8192 token（`in_cap_ok`）。

### 为满足规则做的调整（在任何运行之前）
1. Decode_burst：14b 爆发 out 1230 → 1110。1230 时 14b 受 KV 限制，按形状 ρ 2.25 = 3 副本，和重叠的 7b 衰减（2）、8b（1）合计需要 9 卡 > 8（评审怀疑的 460–580 s 隐性争用，确认存在）。1110 时按形状 1.95 = 2 副本。14b 的 R5 写明豁免（加法 1.83，按形状 1.95）。8b 保持 1200（按形状 3.25 = 4 副本，当时合计 4 + 1 + 2 = 7）。
2. Prefill_mix：窗口顺序改为上表。原顺序 (P, D, B)、(D, B, P)、(B, P, D) 让受 KV 限制的 8b decode 重阶段（按形状 3.08 = 4 副本）和 14b prefill 重阶段（4 卡）同时出现：4 + 1 + 4 = 9 > 8。形状和速率都没改。
3. Tight_pool：三个模型各激增一次（用户要求）。三个 150 s 激增加 90 s 引导，只能放下 90 s 的间隔（评审建议 150 s）。流体检查：30 s 反应滞后下，14b 在下一个激增前回到 2 副本且积压排空（8b 激增后 291 s，7b 激增后 531 s，下一个激增 330 / 570 s）。代价：14b 激增后没有尾段，14b 的 R2 不判（被 trace 结束截断）。

## 4. t0 之前的历史（`pre_t0.json`，给 PreServe 预热，v1 #8）
- 规则写在每个合成 spec 的 `pre_t0` 里：一次性事件的 trace（Tight_pool、Simul_spike、Decode_burst、Prefill_mix）用 `baseline`（按 t = `at_s` = 0 的速率和长度）；周期 trace（Sinusoidal）用 `previous_period`（t mod 360）。时长 750 s = 25 个 30 s 窗口。
- 生成方式：和 trace 相同的逐模型过程（thinning 泊松到达 + 同一长度模型），用独立的随机流（`pre_t0-arrivals` / `pre_t0-lengths`），所以 trace 本身的 design 字节不受影响（有测试）。
- 文件格式 `tre-pre-t0-v1`（JSON）：
  - 头部：`format, trace, seed, rule{rule, duration_s, window_s, at_s | period_s}, t0_s (0), duration_s, window_s`；
  - `windows`：`{model: [{start_s, end_s, requests, prompt_tokens, output_tokens}, …]}`，start_s 从 −750 到 −30；
  - `requests`：`[{request_id: "pre_NNNNNN", timestamp (< 0), model_name, prompt_length, max_output_tokens}, …]`（没有 prompt 文本）。
- manifest 的 `pre_t0` 字段记录 file、format、sha256、rule、requests、每模型请求数。Real_* 没有这个文件（PreServe 用 Azure 里切片之前的窗口，另行处理）。

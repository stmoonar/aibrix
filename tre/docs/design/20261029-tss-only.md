# TSS only: no O1, no saturation rescue, LOW takes from IDLE / HIGH only (2026-10-29)

User decision 2026-10-29. Branch `feat/tss-only-20261029` (on `feat/single-loop-20261028`
@ f00c31de). Tests: `controller/tests/test_tss_only_20261029.py`.

## What was removed, and why

The signal had grown a second decision path around TSS: hold rules for the time after a
routable change, an exempt path for those holds, and a rescue that ignores TSS. Each
one was a timer or a state machine whose job was to hide window lag. They interacted
(10-28 review), and none of them is a correctness guard. Removed:

- **O1 breakpoint window**: breakpoint tracking, effective window and its suffix,
  `settle_breakpoint_ms`, `hold_max`, suspend / resume and the gateway clock check
  (`breakpoint_window_suspended`, `gateway_clock.py`), the EMA reset at a breakpoint,
  `signal_warm` / `signal_hold_reason` holds, the O1 donor / receiver holds and the
  IDLE-window donor excuse. Z now always comes from the **whole 20 s sliding window plus
  the EMA** (v1 behaviour). The idle-window EMA reset stays.
- **H3 exempt path** (`queue_rise`, `QUEUE_*`, `unsettled_upscales`,
  `receiver_o1_exempt_*`).
- **Saturation rescue** (`signals/saturation.py`, its tick hooks, tier ordering and
  events). Rescue order is TSS CRITICAL by Z ascending.
- **C1 rescue-target timing hold** (wait until the window / EMA reflects a target). The
  ledger stays: a target the fleet view does not show yet counts as covered, so one
  plan never counts it twice.
- **F4 action cooldown** (`TRE_ACTION_COOLDOWN`) and the **onset warmup guard**
  (`TRE_SIGNAL_WARMUP_MS`). Both were signal-lag holds. The env names are retired
  (warn and ignore).
- Registry keys `scaling.breakpoint_*`, `onset_warmup_guard`, `min_evidence_requests`,
  `rescue_settle_ema_k`, `gateway_clock_*`, `saturation_*` go to `RETIRED_SCALING_KEYS`
  (warn and ignore), so the live ConfigMap still loads. `scaling.min_evidence_ms` stays:
  SafeScale's early commit reads it.
- Metrics fields only these rules read (`latest_*`, `scrape_fresh`,
  `scrape_stale_inflight`, `scrape_current_pods`, `gateway_inflight`) - rule 3.

**LOW donors.** A LOW receiver takes only from IDLE and HIGH donors. A HEALTHY donor
never gives to LOW: no TP1 `low_fairness_middle_zone`, no TP2 `cheapest_block` HEALTHY
tier. CRITICAL keeps HEALTHY donors (TP1 middle zone, TP2 HEALTHY block). Evidence: in
the 10-28 Tight_pool smoke, 14b went 1 <-> 2 replicas 5 times, driven by
`low_fairness_middle_zone` / `low_fairness_block_healthy` moves.

## Guards that remain (correctness only, no timer)

1. **In flight**: a model with a queued or running SM call gets no new action.
2. **SafeScale probe open**: a probe's donor and receiver wait for its verdict; a
   rolled-back probe waits for new evidence (unchanged).
3. **View pending**: the model's last routable-changing SM call returned after the SM
   state of this tick's fleet view was produced. Since 10-29 this holds **every model in
   every direction** (CRITICAL receivers too). It ends with the next view (F2 refresh).
4. Sample quality (I4): a donor whose window samples are incomplete gives nothing.

## Expected consequence (accepted, not guarded)

The window lags a routable change by up to 20 s (plus the EMA). User decision
2026-10-29: no donor evidence rule and no hold for this; it is observed in the smoke.

- **Over-scale of 1-2 replicas** in a spike: CRITICAL keeps showing after a wake until
  the new replica's grids fill the window. The rebalance section returns the surplus
  when the model reads HIGH / IDLE.
- **Donor cascade, SafeScale on (scope `all`)**: after a donor probe commits, the 20 s
  window still shows the old count, so the donor stays HIGH and a second shrink probe
  starts in the same tick. If the remaining pods overload, SafeScale rolls it back about
  40 s later (`period_sim` "shrink": commit at ~32 s, second probe rolled back at
  ~72-78 s).
- **Donor cascade without a probe** (`TRE_SAFESCALE_SCOPE=receiverless_shrink` for a
  donor with a receiver, or `TRE_ABLATION_DISABLE_SAFESCALE=true`): HIGH-donor releases
  are immediate relays. Nothing checks them afterwards, so one HIGH donor may give a
  replica in every plan (one per plan: `gave_this_plan`; view-pending until the next
  view) for the ~20-30 s the window needs to show the new count. Floor headroom is the
  only bound.

## Stuck engine (TSS definition)

The window is idle (TSS / Z undefined) only when running + waiting == 0 over the window
(`tre_common.tss.window_is_idle`, the same predicate online and offline). Zero tokens
with a queue is not idle: TSS = 0, Z = 0, CRITICAL. A zero is an ordinary EMA sample.
The low-request-rate HEALTHY shortcut does not apply to Z = 0. Missing data stays as
before: tokens unknown -> held; zero tokens in a window with stale or sample-incomplete
pods -> Z unknown, EMA reset, no action. Offline note: the θ fit
(`calibration_window_from_row`) still drops zero-token rows before labelling
(`deploy/scripts/analysis/h_dropped_windows.py`); calibration was not changed.

## How to see it in a smoke

- Events that still exist: `view_pending_hold:<model>:<dir>`,
  `rescue_target_hold:...`, `donor_suppressed_samples_incomplete:<model>`,
  `safescale_rollback_hold:...`.
- Events that must not appear: `breakpoint_*`, `saturation_rescue*`,
  `receiver_o1_exempt_*`. Action reasons that must not appear:
  `low_fairness_middle_zone*`, `low_fairness_block_healthy`.
- Count scale-ups per model after a spike, HIGH-donor probes that start within 20 s of a
  commit and roll back, and (receiverless_shrink arm) consecutive relays from one HIGH
  donor within 30 s. Rebalance should undo the over-scale within about a minute.
